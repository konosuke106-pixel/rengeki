# レートとランキング 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Google ログインしたプレイヤーどうしのランダム対戦の結果で Elo レートを動かし、ランキング画面で上位100人と自分の順位を見せる。

**Architecture:** 計算と記録はすべて Supabase の Postgres の関数（`security definer`、本人確認は `auth.uid()`）。ゲームは `src/account.js` でログインと関数呼び出しをまとめ、`main.js` が画面と試合の流れにつなぐ。ゲストは今まで通り supabase-js を読み込まない。

**Tech Stack:** 素の JS（ビルドは import/export を外して連結）、supabase-js 2.45.4（jsDelivr）、Supabase Auth（Google, PKCE）、Postgres + RLS + pg_cron、node:test。

**Spec:** `docs/superpowers/specs/2026-11-19-ranking-design.md`

## Global Constraints
- ログインしなくても全モードを今まで通り遊べる。レートが付かないだけ
- 本名・メールは他人に見せない。表示名は2〜12文字で本人が決める
- レートはランダム対戦・2人ともログイン済みの時だけ。部屋コードの対戦は付けない。同じ相手とは1日5回まで数える
- Elo：初期 1500、試合数20未満は K=40、それ以降 K=24、最低 100
- 2人の報告が一致した時だけ動かす。食い違いは動かさない。片方だけなら10分後にその結果を採用。2人とも「相手が切れた」は動かさない
- 書き込みは関数経由のみ（表は RLS で直接書けない）。鍵や秘密はチャット・リポジトリに書かない
- `sim.js` には一切触らない。各ファイルの最上位の名前は重複させない（ビルドが連結する）
- 新しい画面の文は `T()`／`data-i18n` を通し、4言語の訳を足す（`tests/i18n.test.mjs` が見張る）

## Review Focus
- 試合の途中で相手が切れた／自分がタブを閉じた：切れた側だけが負け、残った側の報告で10分後に確定（Task 1 のテスト「片方だけ」）
- 同じ報告を2回送る（送り直し）：レートが二重に動かない（Task 1 のテスト「二重報告」）
- 片方がゲスト、または表示名をまだ決めていない：レートなしで普通に試合できる（Task 4 のテスト）
- ログインの途中で戻ってきた URL（`?code=`）を開いたまま再読み込み：エラーにならずログイン済みかゲストになる（Task 3 の手動確認）
- アカウント削除：成績・報告・ランキングから消え、他人の rated_matches は相手の id が消えても壊れない（Task 1 のテスト「削除」）

### Task 1: サーバーの表と関数

**Files:**
- Create: `supabase/migrations/20261119_ranking.sql`（記録用。同じ中身を `apply_migration` で適用）
- Create: `supabase/tests/ranking.sql`（`execute_sql` で流す。`begin; … rollback;` で何も残さない）

**Interfaces:**
- Produces（すべて `public.`、ログイン中の本人として呼ぶ）:
  - 表 `profiles(id uuid pk → auth.users on delete cascade, name text 2〜12文字, rating int 1500, games int 0, wins int 0, created_at)`：select は誰でも可、書き込み不可
  - `set_name(p_name text) returns profiles`（無ければ作る）
  - `my_profile() returns profiles`（無ければ null）
  - `start_match(p_room text, p_gen int, p_opp uuid) returns void`
  - `report_match(p_room text, p_gen int, p_opp uuid, p_result text) returns jsonb` — p_result は `win|loss|draw|dc`。確定したら `{"delta": int, "rating": int}`、未確定・対象外は `null`
  - `ranking() returns table(rank int, name text, rating int, games int, wins int)`（試合数1以上の上位100）
  - `my_rank() returns int`（試合数0なら null）
  - `delete_my_account() returns void`
  - 内部：`finalize_match(p_room text, p_gen int)`、`finalize_stale()`（pg_cron で5分ごと。10分たった片方だけの報告を確定し、1日より古い starts/reports を消す）

- [ ] **Step 1: テストの SQL を書く**（`request.jwt.claims` を `set local` して本人を切り替え、`auth.users` に仮の2人を入れる）。確かめること：
  - 一致：A=win・B=loss → A は 1500+20、B は 1500-20（初期どうし K=40、期待値0.5）、games=1、A.wins=1
  - 食い違い：両方 win → 変化なし
  - 引き分け：両方 draw → 変化なし、games=1
  - 二重報告：A が同じ報告を2回 → 1回分しか動かない
  - 片方だけ：A=win のみ、created_at を11分前にずらして `finalize_stale()` → A+20・B-20
  - 両方 dc → 変化なし。A=dc・B 報告なし → 10分後に A の勝ち
  - start が片方しか無い試合 → 報告しても動かない
  - 同じ2人の6試合目 → delta 0
  - 他人の表は直接 insert/update できない（RLS で失敗）
  - 名前：1文字・13文字は失敗
  - 削除：`delete_my_account()` の後、profiles から消え、`ranking()` に出ない
- [ ] **Step 2: テストを流して失敗を確かめる**（関数が無いので失敗）
- [ ] **Step 3: マイグレーションを書いて `apply_migration` で適用**（Elo：`expected = 1/(1+10^((rb-ra)/400))`、`delta = round(K*(score-expected))`、K は各自の試合数で決める、結果は `greatest(100, …)`。`finalize_match` は同じ (room,gen) を `rated_matches` の主キーで一度だけにする）
- [ ] **Step 4: テストを流して全部通ることを確かめ、`get_advisors`（security）で警告なしを確かめる**
